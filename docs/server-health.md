# Server Health

`ServerHealthSystem` derives the current `HardwareStatus` of every installed
server from simulation state. It turns utilization and representative internal
temperature into a status and a set of explicit alert reasons for consumers such
as a UI.

## Inputs and Outputs

For every server, the system reads:

- `Server.utilization`, produced by `WorkloadSystem`
- the server's current `ServerThermalState`, produced by `TemperatureSystem`
- utilization and temperature thresholds from `ServerHealthOptions`
- the current `HardwareStatus`, so that `OFFLINE` can be preserved

It produces:

- `HardwareStatus.OK` when no monitored alert is active
- `HardwareStatus.ALERT` when `HIGH_UTILIZATION`, `HIGH_TEMPERATURE`, or both are active
- a `ServerHealthState` containing the active alert reasons for that server

The system currently evaluates only utilization and temperature. Other
`ServerAlertReason` enum values are not generated by `ServerHealthSystem`.

## Pipeline Position

Register systems in this causal order:

```text
WorkloadSystem
-> PowerConsumptionSystem
-> TemperatureSystem
-> ServerHealthSystem
-> EnergyConsumptionSystem
```

`ServerHealthSystem` must run after workload and temperature have been updated so
that it evaluates values from the current tick. Running snapshot providers after
the complete pipeline exposes the resulting status consistently.

## Status Lifecycle and OFFLINE Priority

The `status` field in JSON defines a server's initial status. It is not the sole
source of status for the rest of the simulation:

- non-`OFFLINE` servers are automatically recalculated as `OK` or `ALERT` on
  every health-system update
- an initial `ALERT` can return to `OK` if no monitored condition remains active
- a server can move repeatedly between `OK` and `ALERT` as utilization and
  temperature evolve
- `OFFLINE` has priority, is never changed automatically to `OK` or `ALERT`, and
  has its health alert reasons cleared

Calling `ServerHealthSystem.reset()` clears alert reasons and returns every
non-`OFFLINE` server to `OK`; it preserves `OFFLINE`.

## Thresholds and Hysteresis

Each monitored value has two configured limits:

```text
inactive + value >= alertAtOrAbove  -> active
active   + value <= clearAtOrBelow  -> inactive
value between both limits           -> previous state retained
```

Utilization and temperature alerts are tracked independently. A server remains
`ALERT` while at least one reason is active.

Options can be created from the optional JSON `health` block:

```java
ServerHealthOptions healthOptions =
        new ServerHealthOptionsFactory().create(definition);
ServerHealthSystem healthSystem =
        new ServerHealthSystem(datacenter, temperatureSystem, healthOptions);
```

If the block is omitted, the factory uses `ServerHealthOptions.defaults()`. See
[JSON Configuration](configuration.md) for the exact fields, defaults, and
validation rules.

## Health Snapshots

`HealthSnapshotProvider` reads `Datacenter`, `ServerHealthSystem`, and
`TemperatureSystem` without advancing the simulation. `HealthSnapshot` contains:

- `tickIndex`
- `elapsedSeconds`
- one `ServerHealthSnapshot` per installed server
- convenience counts for servers and active alert reasons

Each `ServerHealthSnapshot` contains:

- server identity: `serverCode`, `column`, `rackCode`, and `slot`
- current `status`
- current `alertReasons`
- current `utilization`
- current `temperatureCelsius`

Create it after the simulation tick:

```java
HealthSnapshotProvider provider =
        new HealthSnapshotProvider(datacenter, healthSystem, temperatureSystem);
HealthSnapshot snapshot = provider.snapshot(tick);
```

The snapshot status is the value calculated by `ServerHealthSystem` for that
tick, or the preserved `OFFLINE` value. Snapshot providers contain installed
servers only; empty physical slots still come from the rack layout.
